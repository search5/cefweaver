# llm-wiki 패턴 요약 (카파시)

이 위키가 따르는 패턴의 원문 요약입니다. 원문은 안드레이 카파시가 2026-04-04에 공개한 GitHub gist "LLM Wiki"(`https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f`)이며, 2026-10-08에 원문 파일(`.../raw`, 75줄, 11,985바이트)을 내려받아 전문을 읽고 정리했습니다. 원문은 스스로를 "자신의 LLM 에이전트에게 복사해서 붙여 넣도록 설계된 아이디어 파일"이라고 소개하며, 구체적인 구현은 사용자와 에이전트가 함께 만든다고 밝힙니다.

## 핵심 아이디어

문서와 LLM을 함께 쓰는 보통의 방식은 RAG입니다. 파일을 올리면 LLM이 질문할 때마다 관련 조각을 찾아 답을 만듭니다. 이 방식은 동작하지만 LLM이 질문마다 지식을 처음부터 다시 발견하므로 축적이 없습니다. 다섯 문서를 종합해야 하는 미묘한 질문은 매번 조각을 다시 모아야 합니다. NotebookLM, ChatGPT의 파일 업로드, 대부분의 RAG 시스템이 이렇게 동작합니다.

이 패턴은 다릅니다. LLM이 사용자와 원본 자료 사이에 **지속되는 위키**를 점진적으로 만들고 유지합니다. 위키는 서로 연결된 구조화된 마크다운 파일의 모음입니다. 새 자료를 추가하면 LLM은 색인만 만들어 두지 않고, 읽고 핵심을 뽑아서 기존 위키에 통합합니다. 개체 페이지를 갱신하고, 주제 요약을 고치고, 새 데이터가 기존 주장과 어긋나는 곳을 표시하고, 종합을 강화하거나 반박합니다. 지식은 한 번 컴파일되어 최신으로 유지되며 질문마다 다시 유도되지 않습니다.

핵심 차이는 위키가 **지속되고 누적될수록 가치가 커지는 산출물**이라는 점입니다. 교차 참조가 이미 있고, 모순이 이미 표시되어 있고, 종합이 지금까지 읽은 모든 것을 반영합니다. 자료를 추가하고 질문할 때마다 위키는 더 풍부해집니다.

사람은 위키를 직접 쓰지 않거나 거의 쓰지 않습니다. LLM이 모두 쓰고 유지합니다. 사람은 자료를 고르고, 탐색하고, 좋은 질문을 합니다. LLM은 요약, 교차 참조, 분류, 관리 기록처럼 지식 베이스가 시간이 지나도 쓸모 있게 하는 반복 작업을 맡습니다. 원문의 작성자는 한쪽에 LLM 에이전트를, 다른 쪽에 Obsidian을 열어 두고 LLM이 대화에 따라 고친 결과를 실시간으로 훑어본다고 설명합니다. 원문은 이 관계를 Obsidian은 IDE, LLM은 프로그래머, 위키는 코드베이스에 해당한다고 설명합니다.

## 적용할 수 있는 맥락

원문이 드는 예는 다음과 같습니다.

- 개인: 목표, 건강, 심리, 자기계발을 일지와 기사와 팟캐스트 메모로 쌓아 가는 경우
- 연구: 몇 주나 몇 달 동안 한 주제를 깊이 파면서 진화하는 논지의 위키를 만드는 경우
- 책 읽기: 장마다 인물, 주제, 줄거리 가닥의 페이지를 만들어 동반 위키를 만드는 경우(원문은 Tolkien Gateway 같은 팬 위키를 예로 듭니다)
- 사업과 팀: Slack, 회의록, 프로젝트 문서, 고객 통화를 먹이는 내부 위키. 사람이 검토하는 단계를 둘 수 있습니다.
- 경쟁 분석, 실사, 여행 계획, 강의 노트, 취미 탐구처럼 시간에 걸쳐 지식이 쌓이는 모든 경우

## 아키텍처: 세 층

1. **원본 자료**: 직접 고른 문서 모음(기사, 논문, 이미지, 데이터 파일)입니다. 불변이며 LLM은 읽기만 하고 수정하지 않습니다. 진실의 원천입니다.
2. **위키**: LLM이 생성한 마크다운 파일의 디렉터리입니다. 요약, 개체 페이지, 개념 페이지, 비교, 개요, 종합이 들어 있습니다. LLM이 이 층을 전적으로 소유하며 페이지를 만들고, 새 자료가 오면 고치고, 교차 참조를 관리하고, 일관성을 유지합니다. 사람은 읽고 LLM이 씁니다.
3. **스키마**: 위키의 구조, 규칙, 자료를 받아들이거나 질문에 답하거나 위키를 유지할 때의 작업 절차를 LLM에게 알려 주는 문서입니다(Claude Code는 `CLAUDE.md`, Codex는 `AGENTS.md`). 이것이 LLM을 일반 챗봇이 아니라 규율 있는 위키 관리자로 만드는 핵심 설정이며, 사용자와 LLM이 도메인에 맞게 시간을 들여 함께 고쳐 갑니다.

## 작업

- **ingest(반영)**: 새 자료를 원본 모음에 넣고 LLM에게 처리를 맡깁니다. 예시 흐름은 이렇습니다. LLM이 자료를 읽고, 핵심을 사용자와 논의하고, 위키에 요약 페이지를 쓰고, 색인을 갱신하고, 위키 곳곳의 개체와 개념 페이지를 갱신하고, 기록에 항목을 덧붙입니다. 자료 하나가 10개에서 15개 페이지에 영향을 줄 수 있습니다. 작성자는 자료를 하나씩 반영하며 요약을 읽고 갱신을 확인하고 강조할 점을 안내하는 방식을 선호하지만, 감독을 줄이고 여러 자료를 한꺼번에 반영할 수도 있습니다. 자신에게 맞는 흐름을 만들어 스키마에 적어 두어야 이후 세션이 이어받습니다.
- **query(질문)**: 위키에 질문하면 LLM이 관련 페이지를 찾아 읽고 인용과 함께 답을 종합합니다. 답은 질문에 따라 마크다운 페이지, 비교 표, 슬라이드(Marp), 차트(matplotlib), 캔버스 등 여러 형태가 될 수 있습니다. 중요한 통찰은 **좋은 답변을 새 페이지로 위키에 되돌려 저장할 수 있다**는 점입니다. 요청한 비교, 분석, 발견한 연결은 가치가 있으므로 대화 이력에 사라지면 안 됩니다. 이렇게 하면 탐색도 반영된 자료처럼 지식 베이스에 쌓입니다.
- **lint(점검)**: 주기적으로 LLM에게 위키의 상태 점검을 시킵니다. 페이지 사이의 모순, 새 자료가 대체한 오래된 주장, 들어오는 링크가 없는 고아 페이지, 언급되지만 자기 페이지가 없는 중요한 개념, 빠진 교차 참조, 웹 검색으로 채울 수 있는 자료의 빈틈을 찾습니다. LLM은 조사할 새 질문과 찾아볼 새 자료를 제안하는 데도 능숙합니다.

## 색인과 기록

위키가 커질 때 LLM과 사람이 길을 찾도록 돕는 두 특수 파일이 있고, 목적이 다릅니다.

- **index.md**는 내용 중심입니다. 위키의 모든 것을 링크, 한 줄 요약, 날짜나 자료 수 같은 선택 메타데이터와 함께 분류별(개체, 개념, 자료 등)로 나열한 카탈로그입니다. LLM은 반영할 때마다 갱신하고, 질문에 답할 때는 색인을 먼저 읽어 관련 페이지를 찾은 뒤 들어갑니다. 중간 규모(자료 약 100개, 페이지 수백 개)에서는 놀라울 만큼 잘 동작하며 임베딩 기반 RAG 인프라가 필요 없습니다.
- **log.md**는 시간순입니다. 반영, 질문, 점검 같은 일의 덧붙이기 전용 기록입니다. 모든 항목을 `## [2026-04-02] ingest | 문서 제목`처럼 일관된 접두사로 시작하면 간단한 유닉스 도구로 읽을 수 있습니다. `grep "^## \[" log.md | tail -5`가 최근 다섯 항목을 보여 줍니다. 위키가 어떻게 진화했는지 타임라인을 주고, LLM이 최근에 한 일을 이해하도록 돕습니다.

## 선택 사항: CLI 도구

위키가 커지면 LLM이 위키를 더 효율적으로 다루게 하는 작은 도구를 만들고 싶어집니다. 가장 먼저 떠오르는 것이 위키 페이지의 검색 엔진입니다. 작은 규모에서는 색인 파일로 충분하지만 커지면 제대로 된 검색이 필요합니다. 원문은 `qmd`(`https://github.com/tobi/qmd`)를 좋은 선택지로 소개합니다. 마크다운용 로컬 검색 엔진으로 BM25와 벡터를 섞은 검색과 LLM 재순위를 모두 기기 안에서 수행하며, LLM이 셸로 부르는 CLI와 네이티브 도구로 쓰는 MCP 서버를 모두 제공합니다. 필요하면 LLM과 함께 단순한 검색 스크립트를 직접 만들 수도 있습니다.

## 팁

- Obsidian Web Clipper는 웹 기사를 마크다운으로 바꾸는 브라우저 확장이며 원본 모음에 자료를 빠르게 넣는 데 유용합니다.
- 이미지를 로컬에 내려받아 두면 URL이 끊어져도 LLM이 이미지를 직접 볼 수 있습니다. LLM은 인라인 이미지가 있는 마크다운을 한 번에 읽지 못하므로 텍스트를 먼저 읽고 이미지를 따로 보는 우회가 필요합니다.
- Obsidian의 그래프 보기는 위키의 모양(무엇이 무엇과 연결되는지, 허브와 고아)을 보는 가장 좋은 방법입니다.
- Marp는 마크다운 기반 슬라이드 형식이며 위키 내용으로 발표 자료를 만들 때 유용합니다.
- Dataview는 페이지 frontmatter에 질의를 실행하는 Obsidian 플러그인입니다. LLM이 YAML frontmatter(태그, 날짜, 자료 수)를 넣으면 동적 표와 목록을 만들 수 있습니다.
- 위키는 마크다운 파일의 git 저장소일 뿐이므로 버전 이력, 분기, 협업을 공짜로 얻습니다.

## 왜 동작하는가

지식 베이스를 유지할 때 번거로운 부분은 읽기나 생각이 아니라 관리 작업(원문의 표현은 bookkeeping)입니다. 교차 참조 갱신, 요약을 최신으로 유지하기, 새 데이터가 옛 주장과 어긋나는 곳 표시하기, 수십 페이지의 일관성 유지가 그렇습니다. 사람은 유지 부담이 가치보다 빨리 커지기 때문에 위키를 포기합니다. LLM은 지루해하지 않고, 교차 참조 갱신을 잊지 않고, 한 번에 15개 파일을 고칠 수 있습니다. 유지 비용이 거의 0이라서 위키가 유지됩니다.

사람의 일은 자료를 고르고, 분석을 이끌고, 좋은 질문을 하고, 그 모든 것의 의미를 생각하는 것입니다. 나머지는 LLM의 일입니다. 원문은 이 아이디어가 버니바 부시(Vannevar Bush)의 1945년 Memex, 즉 문서 사이에 연상의 흔적이 있는 개인적으로 선별된 지식 저장소와 정신이 닿아 있다고 말합니다. 부시의 구상은 오늘날의 웹보다 이쪽에 가까웠습니다. 사적이고, 적극적으로 선별되며, 문서 사이의 연결이 문서만큼 가치가 있다는 것입니다. 그가 풀지 못한 부분은 누가 유지하느냐였고, 그것을 LLM이 맡습니다.

## 원문의 단서 조항

원문은 의도적으로 추상적이라고 밝힙니다. 아이디어를 설명할 뿐 특정 구현을 말하지 않습니다. 디렉터리 구조, 스키마 관례, 페이지 형식, 도구는 도메인, 취향, LLM에 따라 달라집니다. 위에 나온 모든 것은 선택적이고 모듈식이므로 쓸모 있는 것만 고르면 됩니다. 예를 들어 자료가 텍스트뿐이면 이미지 처리가 필요 없고, 위키가 작으면 색인만으로 충분하며 검색 엔진이 필요 없고, 슬라이드에 관심이 없으면 마크다운 페이지만 쓰면 됩니다. 올바른 사용법은 문서를 LLM 에이전트와 공유하고 함께 자신에게 맞는 버전을 만드는 것입니다.
