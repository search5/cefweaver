# 위키 스키마

이 문서는 위키의 구조와 규칙을 정의합니다. 어떤 LLM이 작업을 이어받더라도 이 규칙을 그대로 따라야 합니다. 카파시(Andrej Karpathy)의 llm-wiki 패턴을 이 저장소에 맞게 구체화한 것이며, 패턴 자체는 [llm-wiki 패턴 요약](pages/summaries/karpathy-llm-wiki.md)에 있습니다. 규칙이 실제로 맞지 않으면 사람과 LLM이 함께 이 문서를 고치고, 고친 내용을 log.md에 기록합니다.

## 1. 원칙

- 위키는 LLM이 작성하고 유지합니다. 사람은 자료를 고르고, 방향을 정하고, 질문합니다.
- 원본 자료는 위키 작업 중에 수정하지 않습니다. 개발로 원본이 바뀌면 같은 작업 안에서 영향받는 페이지를 ingest 절차로 갱신합니다.
- 사실은 원본을 직접 읽고 확인한 내용만 씁니다. 추측은 쓰지 않습니다.
- 실험으로 확인한 사실은 명령, 환경, 결과, 일자를 [실험으로 확인한 사실](pages/reference/verified-findings.md)에 남깁니다.
- 원본을 끝까지 추적해도 근거를 얻을 수 없는 항목만 [알려진 제약과 미검증 항목](pages/reference/known-constraints.md)에 모읍니다. 그 경우 근거를 얻을 수 없는 이유와 얻는 구체적 방법을 함께 적습니다.
- 문서와 소스가 다르면 소스를 따르고, 불일치를 known-constraints에 기록합니다. 원본 문서가 언급한 대상이 소스에 없으면 미확인이 아니라 불일치로 기록합니다.
- 좋은 답변과 분석은 대화 속에 사라지게 두지 않고 `analyses/` 페이지로 환원합니다.

## 2. 세 층 구조

| 층 | 이 저장소에서 | 소유 |
| --- | --- | --- |
| 원본 자료 | 저장소의 코드와 문서(`native/`, `cefweaver/`, `tools/`, `tests/`, `cmake/`, `CMakeLists.txt`, `pyproject.toml`, `README.rst`, `CLAUDE.md` 등). 조사 대상인 다른 프로젝트(cefpython, java-cef, CEF)의 소스와 위키, 사용 중인 CEF 배포본의 헤더(`build/native/cef/include`)도 읽기 전용 자료입니다. | 사람과 개발 작업 |
| 위키 | `llm-wiki/` | LLM |
| 스키마 | 이 문서와 저장소 루트의 `CLAUDE.md` | 사람과 LLM이 함께 |

저장소 밖의 자료를 근거로 쓸 때는 본문에 경로와 버전(또는 커밋)을 적습니다. frontmatter의 `sources`에는 저장소 안의 실제 파일만 적을 수 있습니다.

## 3. 디렉터리 구조

```
llm-wiki/
  README.md      목적과 사용법
  SCHEMA.md      이 문서
  index.md       모든 페이지의 분류별 목록 (질문에 답할 때 가장 먼저 읽습니다)
  log.md         시간순 작업 기록 (덧붙이기 전용)
  lint.py        점검 도구 (표준 라이브러리만 사용)
  pages/
    concepts/    개념 (type: concept)
    components/  구성요소 (type: component)
    procedures/  절차 (type: procedure)
    reference/   참조, 용어집, 제약, 실험 기록 (type: reference)
    summaries/   원본 문서의 요약 (type: summary)
    analyses/    질문에 답하며 만든 분석과 비교 (type: analysis)
```

## 4. 페이지 형식

모든 페이지는 아래 frontmatter로 시작합니다. 항목은 Obsidian의 Dataview 같은 도구가 읽을 수 있는 YAML입니다.

```
---
title: 페이지 제목
type: concept | component | procedure | reference | summary | analysis
sources:
  - 저장소 루트 기준 원본 경로
updated: YYYY-MM-DD
---
```

- `title`: 한국어 제목입니다. 식별자는 원문을 유지합니다.
- `type`: 위 여섯 값 중 하나이며 페이지가 놓인 폴더와 일치해야 합니다(`concepts`는 `concept`처럼 단수형).
- `sources`: 근거가 된 저장소 안의 파일 경로 목록입니다. 최소 한 개이고 모두 실제로 존재해야 하며, 실제로 읽은 파일만 적습니다. 디렉터리도 허용합니다.
- `updated`: 마지막으로 내용을 확인하고 고친 날짜입니다.
- `generated`(선택): `true`이면 도구가 만드는 페이지입니다. 직접 고치지 않고 길이 제한(200줄)을 적용하지 않습니다. 지금은 [커버리지 보고서](pages/reference/coverage-report.md)가 이 방식이며, `python tools/gen/generate.py`가 쓰고 내용이 같으면 `updated`를 유지합니다.

본문은 `# 제목` 한 개로 시작하고 `##` 절로 나눕니다. 한 페이지는 한 주제에 집중하며 200줄 이내로 유지하고, 넘으면 주제별로 나눕니다. 끝에 `## 관련 페이지` 절을 두어 교차 참조를 나열합니다.

## 5. 명명 규칙

- 파일명은 영문 소문자 kebab-case에 확장자 `.md`입니다. 예: `javascript-bindings.md`
- 파일명은 위키 전체에서 유일해야 합니다.
- 위키 안의 링크는 상대 경로 마크다운 링크만 씁니다. 같은 폴더는 파일명만, 다른 폴더는 `../concepts/x.md`처럼 씁니다.
- 원본 파일은 본문에서 백틱으로 저장소 루트 기준 경로를 표기합니다. 예: `native/cefwrapper/library.cpp`

## 6. 문체 규칙

- 본문은 한국어로 쓰고, 코드, 식별자, 파일 경로, 고유 명사는 원문을 유지합니다.
- 서술어와 종결어미를 갖춘 평서문(`~합니다`)으로 쓰고 조사와 어미를 생략하지 않습니다.
- 엠대시와 비유적 표현은 쓰지 않습니다.
- 확인한 사실과 추론을 구분합니다. 추론은 "추정합니다", "해석합니다" 같은 표현으로 밝힙니다.
- `CLAUDE.md`와 겹치는 내용은 요약하고 원본으로 링크합니다.

## 7. 작업 절차

### ingest (원본 반영)

원본은 가능하면 하나씩 읽고 반영합니다. 한 번의 반영이 여러 페이지(대개 5개에서 15개)에 영향을 줍니다.

1. 반영할 원본(새 파일, 바뀐 코드, 새 문서)을 실제로 읽습니다.
2. index.md에서 영향받는 기존 페이지를 찾습니다. 없으면 새 페이지를 만듭니다.
3. 페이지를 작성하거나 고치고 `sources`와 `updated`를 갱신합니다. 새 자료가 기존 서술과 어긋나면 어긋남을 해당 페이지에 밝히고 known-constraints에도 기록합니다.
4. 관련 페이지의 `관련 페이지` 절에 서로 링크합니다.
5. 새 페이지는 index.md의 알맞은 분류에 한 줄 요약과 함께 등재합니다.
6. 새 용어가 생겼으면 [용어집](pages/reference/glossary.md)을 갱신합니다.
7. log.md 맨 아래에 `## [YYYY-MM-DD] ingest | 제목` 항목을 덧붙입니다.

코드를 바꾸는 개발 작업은 끝나기 전에 이 절차로 위키를 맞춥니다. 어떤 페이지가 영향받는지는 `sources`에 그 파일이 적힌 페이지를 찾아서 정합니다.

```sh
grep -rl "native/cefwrapper/library.cpp" llm-wiki/pages
```

### query (질문 답변)

1. index.md를 먼저 읽고 관련 페이지를 찾아 읽습니다.
2. 페이지에 없거나 오래되었다고 의심되면 `sources`의 원본을 직접 읽어 확인합니다.
3. 답변에 근거 페이지와 원본 경로를 밝힙니다.
4. 답변이 비교, 분석, 새로 발견한 연결처럼 가치가 있으면 `analyses/`에 페이지로 저장하고(ingest 절차 5번까지와 같이 등재), log.md에 `query` 항목으로 기록합니다. 사실이 새로 확인되었으면 해당 개념 페이지도 고칩니다.

### lint (점검)

주기적으로, 그리고 큰 변경 뒤에 점검합니다. 먼저 `python llm-wiki/lint.py`로 기계적으로 확인할 수 있는 항목을 점검하고, 나머지는 읽어서 확인합니다.

기계적 점검(`lint.py`):

1. 모든 상대 링크가 실제 파일을 가리키는지 확인합니다.
2. `pages/` 아래 모든 페이지가 index.md에 등재되어 있는지 확인합니다.
3. 모든 페이지에 frontmatter 네 항목이 있고 `type`이 폴더와 일치하는지 확인합니다.
4. `sources` 경로가 저장소에 존재하는지 확인합니다.
5. 다른 페이지에서 링크되지 않는 고아 페이지를 찾습니다.
6. 200줄을 넘는 페이지와 엠대시 사용을 찾습니다.
7. log.md 항목의 형식을 확인합니다.

읽어서 확인하는 항목:

1. 페이지 사이의 모순을 찾습니다.
2. 원본이 바뀌어 사실과 달라진 서술(오래된 주장)을 찾아 고칩니다.
3. 여러 곳에서 언급되지만 자기 페이지가 없는 개념을 찾아 페이지를 만듭니다.
4. 빠진 교차 참조를 채웁니다.
5. 웹 검색이나 추가 조사로 채울 수 있는 자료의 빈틈을 찾습니다.
6. 더 조사해 볼 질문과 읽어 볼 자료를 제안합니다.

마지막에 log.md에 `## [YYYY-MM-DD] lint | 제목` 항목을 덧붙입니다.

## 8. index.md 형식

분류(폴더)별 `##` 절 아래에 `- [제목](pages/폴더/파일.md): 한 줄 요약` 형식으로 나열합니다. 질문에 답할 때 LLM이 가장 먼저 읽는 파일이므로 요약은 페이지를 열기 전에 관련 여부를 판단할 수 있게 씁니다. 규모가 커져서 index.md만으로 부족해지면 검색 도구를 도입합니다(카파시 문서는 qmd 같은 로컬 마크다운 검색 엔진을 예로 듭니다).

## 9. log.md 형식

시간순으로 파일 끝에 덧붙이고 기존 항목은 고치지 않습니다. 제목 줄은 다음 형식이며 작업 종류는 `ingest`, `query`, `lint`, `schema` 중 하나입니다. 일관된 접두사 덕분에 간단한 도구로 읽을 수 있습니다.

```
## [YYYY-MM-DD] 작업종류 | 제목
```

```sh
grep "^## \[" llm-wiki/log.md | tail -5   # 최근 다섯 항목
```

제목 아래에 변경한 페이지, 근거, 특이사항을 목록으로 적습니다.

## 10. 위키는 git 저장소의 마크다운입니다

위키는 저장소의 파일이므로 버전 이력과 분기를 그대로 쓸 수 있습니다. 위키 변경은 가능하면 관련 코드 변경과 같은 커밋에 넣습니다. Obsidian으로 열면 그래프 보기로 위키의 구조(허브 페이지, 고아 페이지)를 볼 수 있습니다. 이 위키에는 이미지가 없어서 이미지 내려받기 같은 설정은 필요하지 않습니다.
